# Decision log

Dated record of product decisions that changed how the app behaves, as opposed to routine bug fixes or polish. See `docs/08-product-bible.md` for the standing rules these decisions established.

## 2026-07-21 — Motion/colour design language, and scoped dark mode

**Decision:** Separated "the tap" from "the state" in the home screen's animation, and built a four-palette (light/dark × normal/quiet) colour token architecture.

**What changed:**

- The Going quiet / Reconnect tap animations no longer carry any colour or shadow blending — they're now a quick (280ms), purely physical scale change. The emotional colour shift was moved onto the Taking Time state itself, as a separate, slower (1200ms), decoupled fade that triggers on arriving at or leaving that screen.
- The circle's two hardcoded pixel sizes were replaced with one base size plus a single named constant, `QUIET_CIRCLE_SCALE` (`app/index.tsx`), so the resting size is a one-line tuning knob rather than a pair of sizes to keep in sync.
- Taking Time is fully static — no motion at all, on purpose, since it's meant to be genuinely restful rather than quiet-but-animating. The "something is alive" motion belongs to Reconnect instead: the circle grows back out alongside a one-shot ripple that widens and fades (an exhale), the one moment in the flow designed to feel actively in motion.
- `src/constants/theme.ts` was restructured into four palettes (`lightNormal`, `lightQuiet`, `darkNormal`, `darkQuiet`) behind a new `useAppTheme(variant)` hook (`src/hooks/useAppTheme.ts`). All four combinations were checked against WCAG AA contrast minimums before being finalized.

**Scoping decision — dark mode:** building full app-wide dark mode support was clearly a much larger undertaking than the rest of this request, and was called out explicitly rather than silently expanded or silently dropped. The decision made: build the token architecture properly now (all four palettes exist and are correct), but wire live `useColorScheme`-driven switching into the home screen only. The other ~25 files that still import the static `theme` object are unaffected and keep their current (light) appearance regardless of device colour scheme.

**Why:** the home screen is where the Taking Time/Going quiet emotional design actually lives, so it's the place dark mode matters most for this piece of work. Rolling every other screen onto the new hook is mechanical but not free — a bug in this pass shouldn't touch 25 other files' worth of surface area at once.

**Follow-up (not yet scheduled):** roll `useAppTheme` out to the remaining files that currently import `theme` directly, so Dark Mode applies consistently across the whole app rather than just the home screen. Tracked here explicitly so it doesn't quietly get treated as "already done."

## 2026-07-21 — Hold period now ends on actual return, not on opening the Return screen

**Decision:** `endOpenHoldPeriod()` moved from a mount-effect on `app/return/mode.tsx` (fired the instant the user viewed "How would you like to come back?") to the actual completion points: sending the instant message (`app/return/instant.tsx`), and marking a Thoughtful reply as sent (`app/return/reply/edit.tsx` and `app/return/reply/index.tsx`).

**Why:** with the old timing, backing out of the Return flow before actually sending anything — e.g. opening Thoughtful reply, then pressing Back — left the Home screen showing "Going quiet" instead of "Taking time," incorrectly implying the user was no longer in a Hold when nothing had actually been sent. Ending the period only on genuine completion keeps Home's state accurate to reality regardless of how the user navigates the Return flow.

**Doc updated:** `docs/03-privacy-model.md`'s Quiet History section previously documented the old (opens-the-screen) timing explicitly; corrected to describe the new, accurate rule.

## 2026-07-24 — Four-stage journey: Going Quiet, Taking Time, Reconnect, Thoughtful Replies

**Decision:** the app's core journey is now four distinct, separate stages rather than a two-state (quiet/not-quiet) model with an undifferentiated Return flow. Home has three states — Normal ("Going quiet"), Taking Time ("Reconnect" + a new repeatable "Send an update"), and a new Post-Reconnect state ("Finish Reconnecting").

**Persisted audience, not re-picked.** Going Quiet's Circle selection is now multi-select (`GroupPicker`, `HoldFlowContext.selectedGroups`) and is frozen onto the `HoldPeriod` record at send time (`audienceCircleNames`, `audienceContacts` — new optional fields, following the same "frozen at that moment" precedent `docs/03-privacy-model.md` already documents for `recipients`). Reconnect no longer has its own Circle-picker screen at all — it always targets whoever was originally told, even after the app's been fully closed and reopened, since Home always refetches the open Hold period before the user can tap anything. This simplifies `return/mode.tsx` back towards its pre-merge shape (direct-tap options, no shared Continue button) rather than complicating it further, since the reason for the earlier Circle-picker merge no longer applies.

**Two distinct short-message concepts, deliberately separately named** to avoid conflating them: `takingTimeUpdate` (Taking Time's repeatable reassurance, sent without ending Taking Time, `app/return/update.tsx`) and `quickReconnectMessage` (Reconnect's lighter alternative to Thoughtful reply, `app/return/instant.tsx`, backed by new `QUICK_RECONNECT_MESSAGES` copy replacing the old `INSTANT_MESSAGES`).

**Post-Reconnect is a deliberate, considered exception** to the app's usual principle that once a message is sent there's nothing left to do — it's the one point in the journey where something genuinely does stay open, because sending a Quick Reconnect (rather than completing Thoughtful replies) means the user has re-engaged once but not fully. It clears automatically once every in-progress Thoughtful reply is sent, or explicitly via a gentle "Already sorted?" confirmation ("I've already replied" / "I'll reply myself," each behind one extra confirming tap / "Stay in Reconnecting," which does nothing). Tone deliberately avoids "outstanding/incomplete/overdue/pending" language throughout.

**Deferred — Messaging Channels:** per-contact preferred channels (iMessage, WhatsApp, Email, Instagram DM, Messenger, Signal) and a grouped multi-channel delivery screen were explicitly scoped out of this pass, matching the dark-mode precedent above. Today's SMS/share-sheet default is unchanged. Follow-up work, not yet scheduled: `CircleContact` gains per-channel fields, a Circle/contact-settings UI for setting preferred channels, and a delivery screen that hands off to each non-SMS channel's own share/app flow rather than sending directly (e.g. "SMS — sent / WhatsApp — continue / Instagram — continue / Email — continue").

**Also deferred:** a gentle non-urgent reminder to send a Taking Time update after some interval, explicitly marked "not required now" in the request. Tracked here so it isn't mistaken for already built.

## 2026-08-10 — Reconnect's durable marker and Conversations seeding now both set on actual send, not on opening the flow

**Decision:** `beginReconnecting()` (writes the durable `RECONNECTING_KEY` marker Home's resume logic reads) and `seedFromAudience()` (populates the Conversations list with the reconnect audience) both moved from tap-effects on `app/(tabs)/index.tsx`'s `beginReconnect()` — fired the instant "Reconnect" was tapped on Home, before the transition screen or the picker itself had even been seen — to the actual completion point: the first genuine send, inside `app/return/reconnect.tsx`'s `send()`, right after `sendOrShare()` is attempted.

**Why:** with the old timing, backing out of Reconnect before ever sending anything — tapping "Reconnect," then immediately going back — left Home showing "Continue reconnecting" (from the marker) on the next open, incorrectly implying an in-progress Reconnect session when nothing had actually been sent. Moving the marker alone surfaced a second, related instance of the same bug: with Conversations still seeded at tap-time, backing out before sending still left Home falling through to **Post-Reconnect** ("Finish Reconnecting") instead of Normal — a different wrong state, not a fix. Both are the same bug class as the 2026-07-21 `endOpenHoldPeriod()` fix above, one and two steps further into the same journey: a state-changing side effect firing on entering a screen rather than on the action that screen exists to let you take.

**Mechanism:** since `endOpenHoldPeriod()` already closes the Hold period the moment "Reconnect" is tapped (unchanged, and correct — Taking Time genuinely ends there), the period id needed a way to reach `reconnect.tsx` before `RECONNECTING_KEY` exists to point to it. `HoldFlowContext`'s `setAudience()` now also carries `reconnectPeriodId`, and a new `getHoldPeriodById()` lets Reconnect read that specific period directly. `reconnect.tsx`'s `refresh()` now prefers the durable marker when it exists (force-quit-resume, or any visit after the first send) and falls back to the id-based read otherwise — so the picker still has data on a first-ever or backed-out-and-returned visit, without anything durable being written until a message actually goes out. `seedFromAudience()` is called from `send()` using the period's full original audience, not just that send's selection, so anyone not yet individually messaged still ends up in Conversations once the coverage gate is eventually satisfied — not only whoever happened to be in the very first send.

**Back-out paths (Not now, hardware back, swipe-back) needed no explicit cleanup** — since both now only ever run inside `send()`, none of the back-out paths can leave either one behind in the first place; this is prevention, not cleanup, unlike `doClearPostReconnect`'s explicit-dismissal case (2026-07-31 entry above), which still needs its own clear since it fires after real sends have already happened.

## 2026-08-10 — Fixed AdaptiveCircleChip: nothing was actually rendering as a true circle

**Root cause found and fixed.** The prior version measured a label's rendered width via a separate, invisible `position: 'absolute'` + `opacity: 0` `<Text>`, read through `onLayout`. Inside a flex row (a horizontal `ScrollView`'s `contentContainerStyle`, or a wrapping `View`), an absolutely-positioned child with no explicit width doesn't reliably shrink-wrap to its own intrinsic content under every `alignItems`/flex combination — it can pick up ambient sizing from the surrounding row instead. In practice this meant every measured width came back far larger than the actual glyph width, so every label — including single characters like "D" — failed the circle-fits check and fell through to the pill branch every time. Fixed by measuring via `onTextLayout` on the real, always-rendered `<Text>` instead: it reports the rendered line's own width/height directly from the glyph run, independent of any container box, so it isn't subject to that failure mode. It also naturally re-fires on any relayout, including a live font-scale change, so the earlier `useWindowDimensions().fontScale`-driven reset effect was no longer needed and was removed.

**Also corrected while fixing this:** the hard-minimum diameter was being treated as a fixed size rather than a floor. Height (and circle diameter) is now `Math.max(MIN_DIAMETER, measuredTextLineHeight + verticalPadding)` — at default text size this always resolves to exactly `MIN_DIAMETER` (44pt iOS / 48dp Android, both constants, independent of font scale), but at very large accessibility text sizes the container grows to fit the taller measured line rather than clipping it, while never dropping below the minimum either way. Confirmed directly from the code/constants, not by eye: `MIN_DIAMETER` is a literal fixed value used as the floor for every dimension of every shape at every font size, so both shapes stay at-or-above 44×44pt (iOS) / 48×48dp (Android) by construction.

**Also this session:** removed hold-book's older, unbuilt "Core Circle" Library-template-category concept (`04-ux-content/04-navigation-architecture.md`) — a different, older idea using the same word as the new "Core" section heading, confusing rather than disambiguated, confirmed for removal directly. Added a small, muted "Where this comes from" link beneath the Core section's copy in Your Circles, pointing to a new Research entry ("Why 'Core' groups Close and Friends together," citing Dunbar's support-clique/sympathy-group layered model) — links to the general Research screen for now, since anchored entries aren't built yet.

**Flagged, not resolved:** the requested "render and report back" visual verification for the shape fix couldn't be performed from this session — no simulator/screenshot capability here. The measurement logic itself is verified by direct code/constant inspection above, but the actual on-screen render still needs an on-device check.

## 2026-08-10 — The shape fix above didn't actually work; found and fixed the real second bug

**On-device screenshots showed the prior fix hadn't changed anything** — every chip, including "Close" and "All," still rendered as a pill. The `onTextLayout` measurement fix from earlier the same day was itself correct (verified again this pass), but a second, separate bug made the circle branch practically unreachable: `availableCircleWidth = MIN_DIAMETER(44) − 2×HORIZONTAL_PADDING(20) = 24pt`, and "Close" at 14pt/weight 600 renders at roughly 35–40pt of text width using typical San Francisco character-advance metrics — 46–67% over that 24pt threshold, regardless of how accurately it's measured. The circle was never allowed to grow past a fixed 44pt diameter, so nothing but a single narrow character could ever pass.

**Fix:** the circle's diameter now grows to fit the label — `naturalCircleDiameter = Math.max(MIN_DIAMETER, textWidth + padding, textHeight + padding)` — floored at the hard minimum as before, now also capped at a new `MAX_CIRCLE_DIAMETER` (1.5× `MIN_DIAMETER`, i.e. 66pt on iOS) so a genuinely long label doesn't grow into an oversized circular blob; those still fall back to the pill, sized to the text as before. Worked example: "Close" needs ≈55–60pt (under 66 → circle), "All" needs ≈40–44pt (floors to 44 → circle), "D" floors to 44 → circle, "Book Club" needs ≈90–100pt (over 66 → pill).

**Still flagged, not resolved:** this is derived from the code's constants and formula plus estimated font metrics, not an actual on-device screenshot — no simulator/screenshot capability exists in this session. Needs on-device confirmation, same as the prior entry.

**Also this pass:** GroupPicker's "+ New Circle" button now shows just "+" (`accessibilityLabel="New Circle"` added so screen readers still announce it properly), position unchanged since it already sat immediately after "All." Bumped its `minWidth`/`minHeight` from 38pt to 44pt — with the label text gone, padding-plus-glyph math alone would have landed around 41pt wide, under the accessible minimum.

## 2026-08-10 — Circle-chip sizing redesigned: one fixed diameter, not grow-to-fit

**Replaced the whole floor/cap/natural-diameter model with a single fixed `STANDARD_CHIP_DIAMETER`** per direct instruction, since the grow-to-fit design (even once its two bugs were fixed) produced an inconsistent row — "D" at the bare 44pt floor, "Close" at ~57–60pt, a pill at up to 66pt, none sharing a height. `STANDARD_CHIP_DIAMETER = 48pt (iOS) / 52dp (Android)` — platform-specific by design, not one shared cross-platform value, each a flat +4 above that platform's own accessibility minimum (44pt HIG / 48dp Material). Every chip is exactly this tall now, full stop: a circle at exactly this diameter if the label's measured text fits inside it (minus padding), otherwise a pill at the exact same height with only width growing to fit the text — "the same circle, stretched wider," not a separately-sized shape. Height no longer varies with font size at all (an accepted trade-off, flagged: at very large accessibility text sizes a label's line height could exceed the fixed chip height, and `numberOfLines={1}` means it clips rather than wraps or grows the box).

**Worked table, same estimated-metrics caveat as before (14pt/weight 600, San Francisco, not an on-device measurement):**

| Label | Est. text width | Shape | Width | Height |
|---|---|---|---|---|
| "D" | ~9pt | circle | 48pt | 48pt |
| "All" | ~22pt | circle | 48pt | 48pt |
| "+" | ~9–10pt | circle | 48pt | 48pt |
| "Close" | ~37pt | pill | ~57pt | 48pt |
| "Book Club" | ~75pt | pill | ~95pt | 48pt |

All five share the same 48pt height, confirming the redesign's actual goal (row consistency) independent of which ones end up circles vs. pills.

**Also this pass:** found "+" was never actually going through `AdaptiveCircleChip` — it was still a separately hand-styled `Pressable` (the one manually patched to 44×44pt last time), which is exactly why it wouldn't have picked up this sizing change automatically. Brought it into the shared component properly: added `outline` (the bordered/transparent treatment it already had), `accessibilityLabel` (its visible "+" isn't what a screen reader should announce), and `expanded` (it toggles a creation panel, not a selection — reports `accessibilityState={{expanded}}` instead of `{checked}`) props to `AdaptiveCircleChip` to support it without special-casing. Removed the now-dead `newCirclePill`/`newCirclePillPressed`/`newCirclePillText` styles. One small, honest trade-off: the old "+" button had its own `pressed` background-darken effect that `AdaptiveCircleChip` doesn't replicate — no chip in the shared component has press feedback, consistent with how the original `CirclePill` worked too, so this isn't a new gap, but "+" specifically had it before and now doesn't.

**Size, resolved with git history, not a guess.** Checked `CirclePill`'s full commit history: `minHeight: 38` from creation through deletion, unchanged. `STANDARD_CHIP_DIAMETER` reverted from 48/52 (a deliberate "+4 comfortable margin" chosen two passes ago) to 44pt (iOS) / 48pt (Android) — the bare accessibility floor itself, the closest legally-compliant value to 38 since going lower isn't defensible. **Two independent state props replace the single `selected` boolean:** `isSelected` and `hasSentThisSession`, both renamed/added at every call site. ## 2026-08-13 — Nav bar visibility rewritten around a two-tier, screen-category-first rule, replacing the composition-everywhere rule from earlier the same day

`tsc --noEmit` and `vitest run` (27/27) both pass.

**This directly reverses the "hides while composing, everywhere" rule built and documented earlier today** (see the "New nav rule" entry above) — flagged here rather than silently swapped, since the new rule was given as an explicit correction to that one, not an independent request. Old: composition state alone decided visibility, uniformly. New: which screen you're on decides first (Tier 1 — Going Quiet, Transition screens, Reconnect including its resumed state — hidden throughout, no exceptions; Tier 2 — Home, Library, History/Patterns, Settings and sub-screens — visible by default, composition-based hiding only applies *within* this tier).

**A real architectural problem, not just a rule change: Tier 2 explicitly includes Settings, which structurally could never show the nav bar under the old architecture at all.** The bar used to be the Tabs navigator's own `tabBar` render prop (`(tabs)/_layout.tsx`) — by React Navigation's own design, that only ever renders for screens that are direct children of that one navigator. Settings (`settings/mission`, `settings/privacy`, etc.) are pushed root-stack screens, siblings of `(tabs)` itself in `app/_layout.tsx`, not children of it — no `tabBar` prop belonging to the Tabs navigator could ever reach them, regardless of its own visibility logic. Same was already true of Going Quiet/Reconnect/Transition (noted in the earlier entry), but there it happened to match the desired behaviour (hidden); for Settings it directly contradicts it.

**Fixed by moving the bar out of the Tabs navigator entirely, to a root-level overlay:** `(tabs)/_layout.tsx`'s `Tabs` now passes `tabBar={() => null}` (renders nothing of its own); `BottomTabBar` is mounted once in `app/_layout.tsx`, a sibling of `<Stack>`, absolutely positioned so it can float over any screen regardless of which navigator owns it. It no longer takes navigator-supplied props (`state`/`descriptors`/`navigation`) — it reads `usePathname()` directly for Tier 1/2 and current-tab-highlight, and calls `router.navigate()` itself for tab switches (confirmed no code anywhere listened for the old `tabPress` event it used to `emit`, so nothing was lost dropping that).

**The old `hideTabBar` mechanism (a per-screen `navigation.setOptions` option, read via `descriptors[focusedRoute.key]`) has no equivalent once the bar is outside the Tabs navigator** — there's no descriptor to read. Replaced with a new `ComposingContext` (mirrors `QuietPaletteContext`'s shape) that `useComposingGestureLock` now writes to instead. **A real subtlety the old mechanism got for free and this one had to rebuild explicitly:** the old check was scoped to the *focused* route's own descriptor, so composing on Library then switching to History never left History's bar wrongly hidden. A shared, non-scoped context boolean doesn't have that isolation on its own — `useComposingGestureLock` now uses `useFocusEffect`, not a plain `useEffect`, writing `isComposing` only while its owning screen is actually focused and explicitly clearing it on blur (not just unmount, since a Tab screen like Library never unmounts when switching tabs, only loses focus) — without this, composing on Library then switching tabs would leave the bar hidden everywhere until Library happened to recompute state again.

**A side effect of leaving the Tabs navigator, fixed rather than left as a regression:** React Navigation automatically reserves bottom layout space on sibling screens for a navigator-managed custom `tabBar` (it measures the bar's own height and pads accordingly) — a root-level absolute overlay gets none of that for free, so screen content would scroll under the floating pill with no clearance. New `src/utils/navTier.ts` centralises the Tier 1 route-prefix check (shared by `BottomTabBar` and `Screen`, so the two can't drift out of sync) plus a `NAV_BAR_RESERVED_HEIGHT` constant (deliberately approximate, not pixel-exact). `Screen.tsx` now conditionally adds this to its content/footer bottom padding on Tier 2 routes only — Tier 1 screens get no added whitespace, matching that the bar never shows there either way. Home doesn't use `Screen` (its own `SafeAreaView`/`ScrollView` layout) — reserved unconditionally there instead, since Home is always Tier 2.
